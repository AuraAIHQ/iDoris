## 1. 一句话

```
Agent24  做事      iDoris  准入      Hyphae  传话      agentEar  听与说
```

四者**不是四层，是四种权限域**。它们各自持有一条别人不能替它执行的规则，组装起来才是「个人 / 组织的智能大脑」。

## 3. 逐个组件：只负责什么 / 明确不负责什么

| 组件 | 只负责 | 明确**不**负责 | 独占的不可破规则 |
|:---|:---|:---|:---|
| **Agent24** | Skill / agent 执行、会话生命周期、工具调用、插件与 OS 配置定义业务场景 | 部署全栈、保存所有密钥、语音流、租户账本 | **危险动作必须过审批门** |
| **iDoris** | 推理资源**准入**：租户身份→策略、预算/配额、provider 凭证、隐私策略判定、用量账本、远程请求出口 | agent 工作流、原始音频、长期记忆、DID 私钥、业务语义 | **LocalOnly 绝不出设备** · **预算是拒绝不是降级** · **租户预算/用量硬隔离** |
| **Hyphae** | Nostr 传输、节点发现、加密信封、投递确认 | 协作工作流、任务仲裁、重试/超时/补偿、业务状态机 | **agent 间消息端到端加密（NIP-44）** |
| **AgentEar**（外部组件，非 iDoris 子模块）| **输入法组件**：收音、VAD、唤醒词、分段、打断；**「说话器官」**：可插入任意 agent 的语音出口；本地 ASR/TTS 运行时；知识库投递与标签路由 | 通用文本路由、组织预算、跨租户策略 | **原始录音不出机器** |
| **AirAccount** | DID、身份绑定、签名、授权根 | provider key、模型路由 | **私钥不离持有方** |
| **MemPalace** | 跨会话 / 跨 agent 的长期记忆及其生命周期（命名空间、来源、保留、删除、导出） | agent 执行、推理准入 | **记忆不跨租户/跨 subject 串线** |
| **模型制品层** | 权重下载、哈希与签名校验、许可证、版本固定、缓存配额、回滚 | 推理策略、租户计费 | **未验签的权重不得载入** |
| **brain-dist** | 安装、配置 schema 与启动前校验、版本兼容矩阵、升级/回滚、健康检查 | 任何运行期业务决策 | **只布线密钥引用，不读明文** |

## 4. 三条关键边界（最容易打架的地方）

### 4.1 iDoris 的边界不是「智能」，是**权限**

原表述「iDoris 负责所有智能处理」不可执行——隐私分类、文档解析、提示构造、记忆检索、工具选择、ASR、TTS、Embedding 都能叫「智能处理」。照它走，每加一种模态 iDoris 就要长一个后端，最终它同时是策略中心 + 密钥库 + 推理代理 + 租户数据库 + 审计系统，**一个进程挂掉，文本、语音、外部 API 全瘫**。

改成按权限定义：

> **iDoris 决定「哪个租户，在什么预算与隐私策略下，可以访问哪些推理资源」。它不天然拥有每一种模型运行时。**

**因此被保护的不变式也要改**。原来想守的是「所有模型请求都过 iDoris」，实际该守的是：

> **所有远程的、计费的、或受组织策略约束的模型访问，必须经 iDoris 准入；**
> **隐私敏感的纯本地推理可以在可信边缘直接执行，但必须先取得策略授权，并回传不含原始内容的用量与审计凭据。**

前者是组织纪律（谁都可能绕过），后者靠拓扑与沙箱（绕不过）。

### 4.2 语音：控制面与数据面分离（推翻了我的初始倾向）

我原本主张 agentEar 只做 I/O、ASR/TTS 推理回落 iDoris，理由是保住「所有请求过 iDoris」。**这个主张被否掉了，理由比我的更强**：

- 实时音频多一次进程跳转与序列化；流式、取消、背压、采样率协商会全部污染 iDoris 的接口。
- iDoris 是**持有租户凭证和外网出口权限**的进程。把原始录音送进去，**扩大**了泄露面而不是缩小——恰好与「录音不出机器」的承诺相反。
- VAD / partial ASR / 端点检测 / TTS 打断构成一个**反馈环**，不是两个干净的 HTTP 请求。

所以：**agentEar 拥有语音模型的完整生命周期**；iDoris 只签发短期 capability、记录用量、并禁止远程路径。原始音频走 unix socket / loopback，用出站网络限制落实「不出机器」。

> 副作用（好的）：iDoris **不需要**为 M1 引入非-MLX 后端。`06 §10.3` 给 llama-swap 留的那个口子暂时不必打开。

### 4.3 「双 harness 嵌套」必须二选一

下游泰国业务的产品形态是「**Python Harness 托管 Skill**」，而 Agent24 的定位也是「**agent harness**」。两边会自然争夺同一批职责：Skill 加载与版本、输入输出校验、重试与超时、工具权限、审批、会话状态、错误恢复。

**长期保持两个 harness 嵌套，一次请求就会有两套生命周期和两套错误语义。** 必须选一条：

- **(A) Python Harness 只是产品适配层**，真正执行委托给 Agent24；
- **(B) Python Harness 就是产品 runtime**，Agent24 只提供路由 / 审批 / 工具执行等独立服务。

**这条待拍板**，且比 agentEar 的边界更迫近——下游已经在跑 (B) 的形态了。

## 5. 必须立刻处理的两个漏洞

### 5.1 🔴 订阅中转会绕过 Agent24 的审批门

能力① 是 spawn `claude -p` / `codex exec`。**这两个不是纯模型 provider，是具备工具与工作区能力的 agent 程序。** 如果 iDoris 把它们当成「一个 provider」放进推理路径，调用方就获得了一条**绕过 Agent24 审批门执行工具**的通道——审批门管的是 Agent24 自己的动作，管不到 iDoris 里 spawn 出来的 CLI。

**结论**：该适配器必须运行在**无工具、无工作区写权限、无任意子进程能力**的沙箱里；做不到就**不得**放进可信推理路径。这条要写成 T1.4.x 的验收，不是注意事项。

### 5.2 🔴 多租户不会因为「归 iDoris」就自动成立

iDoris 能隔离的只有**预算、用量、provider 凭证**。真正的租户隔离必须由**每个有状态组件各自执行**：

| 组件 | 它必须自己隔离的东西 |
|:---|:---|
| Agent24 | 会话、工具凭证、审批记录 |
| Hyphae | 收件箱、路由元数据、消息保留 |
| agentEar | 录音缓冲、转写缓存、设备权限 |
| MemPalace | 记忆命名空间、删除与导出 |
| 模型制品层 | 租户专属 LoRA、授权权重 |
| iDoris | 预算、用量、provider credential |

> **iDoris 可以是租户身份与策略的权威来源，但不能替其他组件完成隔离。**
> 否则所谓「多租户底座」只隔离了账单，没有隔离数据。这一条要写进对外契约。

## 5.3 事实更正：AgentEar 已存在，且是四者中做得最深的

我在初稿里写过「agentEar 不存在任何仓库」——**那是错的，我的核查范围漏了 `~/Dev/tools/`**。实际是 [`iDoris-ai/AgentEar`](https://github.com/iDoris-ai/AgentEar)，Rust，**M1 + M2 已完成**（v0.4.2），有发布版 `.app`。详见 [`voice-v0-findings.md`](voice-v0-findings.md)。

**定位（2026-09-07 jason 拍板）**：**AgentEar 是外部输入法组件，未来还包括独立的、可插入到任意 agent 的「说话器官」。** 即它既是**入口**（听）也是**出口**（说），且「说话器官」是可被任意 agent 插入的独立件——不是 iDoris 或 Agent24 的子模块。**iDoris 是它的消费者与被消费者，不是它的拥有者**：iDoris 不改它、只提需求；它接 iDoris 拿文本推理。

**这个事实反过来验证了 §4.2 的结论**：AgentEar 已经自己拥有完整的语音运行时（SenseVoiceSmall + FunASR llamacpp + fsmn-vad，泰语另走 whisper.cpp 引擎），且「录音不出机器」本来就是它的设计约束。如果按我最初的倾向 (a) 把 ASR 推理挪进 iDoris，等于**要求重写一个已经跑通并发版的系统**——那不只是过度设计，是破坏。

**更要紧的是它已经是 iDoris 的第二个消费者，而且几乎零成本**：
`src/correct.rs` 与 `src/label.rs` 默认连 `http://127.0.0.1:8793`，发 `POST /v1/chat/completions`，用的模型是 **Ornith——正是 iDoris 选定的常驻核心**。它现在要求用户「自己备一个本地 LLM」；接上 iDoris 只需改一个 URL，并顺带获得隐私路由、预算与审计。

> **规划含义**：iDoris 的 M1 纵切多了一个几乎免费的验收场景。文本推理跑通那一刻，AgentEar 就能指过来——比等泰国业务改完薄客户端更快拿到真实流量。

## 6. 评审采纳与驳回

**采纳**（本稿据此改写）：
1. iDoris 按权限定义而非按「智能」定义 —— §4.1
2. 语音走控制面/数据面分离，推翻我的初始倾向 —— §4.2
3. Hyphae 是传输不是协作编排 —— §3
4. 装配不归 Agent24，另立无常驻服务的发行层 —— §3（理由：负责启动所有进程的组件通常也能读所有配置与凭证，这直接破坏「进程边界=授权边界」）
5. 密钥按权限域拆分，不整体归 iDoris —— §3（「统一管理」与「统一爆炸半径」只差一步）
6. 补齐 MemPalace / AirAccount / 模型制品层 / 全链路审计四处缺失职责
7. 订阅中转绕过审批门 —— §5.1
8. 多租户需各组件各自隔离 —— §5.2
9. M1 做极薄纵切而非一次建完整底座 —— 见 [`roadmap.md`](roadmap.md)

**驳回**：
- **「把 Agent24 的 ModelRouter 拆成独立进程 `agent24-routerd`」** —— 驳回。这是对 Agent24 内核的改造，而 [`../09-对Agent24的需求.md`](../09-对Agent24的需求.md) 的非需求里明确写了「不要求 Agent24 做的事」，iDoris 只提需求不改其内核。**采纳其关切、换一种解法**：Agent24 的 `ModelRouter` **保持不动**，iDoris 作为它的一个 provider 接入（R1，纯加法零回归）；**策略权威归 iDoris，Agent24 侧不新增策略**。两者的重叠靠「只有一个地方长新策略」收敛，而不是靠一次高风险迁移。
- **「不能让零代码项目先获得逻辑所有权」** —— 措辞驳回，实质采纳。设计权归属与实现进度是两件事；但底下那句警告是对的：**不要重写一份 Agent24 已经有的路由**。已写进上一条。
